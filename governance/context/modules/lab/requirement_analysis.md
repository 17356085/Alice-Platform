## 1. 分析业务场景

基于“lab”模块这一名称，可以推断其核心业务场景涉及一个**实验室管理或资源预约系统**。常见的模块功能包括：

*   **实验室资源管理**：管理实验室的名称、位置、设备等基本信息。
*   **实验预约**：用户（教师、学生）查看实验室空闲情况，并预约使用。
*   **预约审批**：管理员或负责人对预约请求进行审批、修改或拒绝。
*   **预约记录与统计**：查看历史预约记录，分析实验室使用率等数据。
*   **设备管理**：管理实验室内的备（如示波器、离心机），包括型号、状态、借用情况等。
*   **用户管理**：将与实验室相关的用户（管理员、普通用户）与实验室/权限关联起来。
*   **学生/教师签到**：在预约时间内进行签到或签退，记录实际使用情况。

**核心业务流程**通常是：
1.  **资源查看**：用户查看实验室列表及其当前状态。
2.  **发起预约**：用户选择时间、用途并提交预约申请。
3.  **审批处理**：管理员审核申请，通过/拒绝。
4.  **执行预约**：用户在预约时间到场并签到。
5.  **使用完毕**：用户签退，释放资源。

## 2. 分解场景并分级 (P0, P1, P2)

根据业务影响和核心流程，我们将测试场景分为三个优先级：

*   **P0 (Critical)**：核心流程功能，直接影响业务可用性。如果失败，系统无法正常使用。
*   **P1 (High)**：主要功能特性，非核心但业务价值高。如果失败，严重影响用户体验或部分业务中断。
*   **P2 (Medium)**：辅助/优化功能，边缘场景。如果失败，不影响主流程，但体验或数据完整性受损。

### P0 场景 (核心业务流程)

1.  **用户查看可用资源列表**
    *   用户成功登录后，能看到所属实验室或全部实验室的列表。
    *   列表应显示实验室状态（空闲/占用/维修）。
2.  **用户发起预约请求**
    *   选择一个空闲的实验室、时间段、填写用途。
    *   系统成功创建预约记录，状态为“待审批”或“已预约”。
3.  **管理员审批预约**
    *   管理员查看所有“待审批”的预约。
    *   管理员执行“通过”操作，预约状态变为“已批准”。
    *   管理员执行“拒绝”操作，预约状态变为“已拒绝”，并可选填原因。
4.  **用户按预约时间使用资源**
    *   用户在预约时间到达，进行签到操作，系统记录签到时间。
    *   预约状态从“已批准”变为“使用中”。
5.  **用户结束使用并释放资源**
    *   用户在使用完毕后，进行签退操作，系统记录签退时间。
    *   预约状态从“使用中”变为“已完成”。
    *   实验室资源状态恢复为“空闲”。

### P1 场景 (主要功能特性)

1.  **时间冲突检测**
    *   用户试图预约一个已经在同一时间段被占用的实验室。
    *   系统应给出明确提示，禁止重复预约。
2.  **预约信息修改/取消**
    *   用户或管理员可以修改（在允许条件下）或取消一个待审批/已批准的预约。
    *   取消后，对应的资源自动释放。
3.  **实验室搜索与过滤**
    *   用户可以根据实验室名称、设备、容量等条件进行搜索和筛选。
4.  **预约日历/看板视图**
    *   系统提供日历或时间线视图，方便用户直观查看特定实验室的长期占用情况。

### P2 场景 (辅助/优化功能)

1.  **管理员管理实验室信息**
    *   添加、编辑、删除一个实验室的基本信息（名称、位置、描述等）。
2.  **设备管理**
    *   为实验室添加、编辑、删除设备信息。
    *   查看设备的借用历史记录。
3.  **预约统计报表**
    *   管理员查看按时间、实验室、用户分类的使用率统计报表。
4.  **用户权限管理**
    *   系统区分“管理员”和“普通用户”角色，不同角色拥有不同权限。（例如：只有管理员能审批，只有普通用户能发起预约）。
5.  **签到/签退超时处理**
    *   用户预约后未在规定时间内签到（例如迟到15分钟），系统自动取消预约并释放资源。
6.  **通知与提醒**
    *   用户提交预约后，系统发送通知给管理员。
    *   管理员审批后，系统发送结果通知给用户。
    *   在预约开始前几分钟，系统发送提醒给用户。
